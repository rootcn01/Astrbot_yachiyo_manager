## 0. 排序与排程建议（总结论）

**W-AH 先启动（观察期=挂历时间 3–7 天）→ W3 编码期与观察期重叠 → D3 分支拍板与 W3 部署压到观察期后 → W4 收尾**。W4 的 livingmemory 写接口验证（只读+测试写入，不部署）插在观察期内并行。

## 1. W-AH · angel_heart 实验窗

### 1.1 目标
重启 angel_heart 0.9.0（07-18 起停用，两个编译靶位已惰性落盘、启用即生效），单一 QQ 金丝雀群验证三判据，产出「保留激活 / 永久停用」的拍板依据。

### 1.2 爆炸半径（对抗修订：白名单不是全局门）
源码级事实（快照取证），启用后**不止金丝雀群**受影响：
- 白名单只是两道局部门：①`_should_process` 的白名单只挡**非@消息**——@/唤醒消息在检查前就放行（main.py:295-357）；②`delegate_prompt_rewriting` 白名单只挡**上下文接管**（main.py:131-134）。
- 因此**任何群**的 @消息都会走缓存→补历史（QQ API 调用）→秘书分析：**每条 @消息 +1 次 analyzer 调用 +回复延迟**，与是否金丝雀无关。
- `strip_markdown_on_decorating_result` 对**所有会话（含私聊）**无白名单门：全局 markdown 清洗、错误消息清链、**全部机器人回复入账 ledger**（私聊内容获得第二份持久化副本，§6 风险登记已记）。
- 扣押机制：同 chat 旧等待事件直接 `set_result("KILL")`（angel_heart_context.py:286-293）→ 清空 chain + `stop_event()`（front_desk.py:439-446）——**密集连@时（含非金丝雀群）@回复可能被静默吞掉**；handle_event 异常路径同样 stop_event（:352-355）。

结论：金丝雀限制的是「插话决策+上下文接管」两个行为面，不是成本面与全局副作用面。判据与回归项按此口径设计（见 1.5）。

### 1.7 判据与冒烟（观察期 ≥3 天）
1. **插话时机质量**（金丝雀群）：非@消息的插话/沉默决策样本 ≥20 条，人工评价合理率；无复读、无连环插话刷屏；proactive 叠加样本按 1.5 归因处理。
2. **注入相互作用**（金丝雀群）：@回复仍含 manager 侧信号（时段/关系称呼）；HISTORICAL MEMORY REFERENCE 块存活；system_prompt 实序=原生协议→manager 块→scene_prompt。**trace 对账的真实代价=两次停机改**（cmd_config 面，开一次关一次=两次 restart+两次 TASKLOG 检查）——默认接受日志级验证；确需 trace 则在一次停机窗口内完成开-测-关。
3. **秘书调用量**：口径=金丝雀群全量消息 **+ 全部群 @消息**；日志统计次数/日、失败率、延迟；确认成本可接受。
4. **回归面**（非金丝雀）：其他群 @消息：回复到达（含连@×5 吞回复测试）、延迟增量可感度、markdown 清洗无感；私聊行为与实验前一致；proactive 推送/分段回复不受影响。
5. 收口：三判据评分 → 用户拍板。保留=常态运行；弃用=回滚，终态成立（@驱动+主动破冰，人格栈完整）。

### 2.2 设计决策（承重点）

**D0 ·（对抗新增，W3 生效前提）修活关系计数**
`_update_user_interaction` 全插件仅 1 个调用点（main.py:140，创建提醒内）——interaction_count 生产中几乎不动，真实用户永远停在 stranger/acquaintance，**选区机制上线即近死代码**。W3 范围必须加：`inject_persona` 成功注入路径调用 `_update_user_interaction`（顺带修活 last_seen/mood 语义）。落盘策略：计数内存累加；relationship 跨档、mood 变化、或距上次落盘 >10min 才写 KV（防每消息一次 KV 写）。冒烟须走真实聊天路径计数，不得只靠手工播种 KV。

**D1 · 静态采样与运行时选区的关系**（建议：协议保留最小兜底采样）
- 建议 A（推荐）：原生协议保留**营业区最小采样**（manager 有跳过条件：persona_enabled=false、群聊非@——这些场景协议是唯一人格来源）；manager 动态层按关系×场景给完整选区，「替换式」=选区档位互斥（按关系给一档，不累积全库）。stranger 档注意：协议营业采样与动态营业区 9 条**内容重复须去重**（动态层选区排除协议已采样条目，或协议采样固定、选区从剩余条目取）。
- 备选 B：静态采样全撤、全靠运行时——manager 跳过场景下语气示范归零，人格塌一角，不推荐。
- 现状事实：`sample_tone_lines()` picks 硬编码 dict，可收缩；NATIVE_HARD=2800 字预算，收缩腾出空间。

**D2 · 台词数据进 manager 的通道**（建议：编译产物同步链）
- build_persona.py 新增产物 `persona/out/tone_zones.json`（三区唯一句+选取规则+版本+源 sha）→ 落点=插件 `resources/tone_zones.json`。
- 打包事实（对抗核实）：build_zip.py 是全目录 walk 白名单排除制——文件放插件目录即自动随包，**build_zip.py 无需改动**；真正要定义的是 ①persona/out→resources 的同步动作（编译后手动/脚本拷贝，写进 runbook）②manager 启动时校验：resources 缺文件或版本落后=启动日志 WARN+退化为不注入选区（**禁静默用旧数据**）③对账方式：manifest 不随插件分发，对账靠 json 内嵌版本/sha + manager 启动日志打印。

**D3 · 群聊风格路由**（对抗重做：原设计两头落空）
时序与覆写事实：①@轮——`force_reply_when_summoned`+`reply_even_not_questioned`（均默认 True）下策略被覆写为字面量**「被呼唤回复」**（secretary.py:171-176），非五枚举之一；②插话轮（非@）——manager 注入被跳过（main.py:667-668），预置在 manager 动态层的映射**不在场**，而插话轮恰是 angel_heart 主战场。
- W-AH 保留分支：映射表加「**被呼唤回复→营业默认**」第六分支；枚举→风格提示**放进原生协议 60-scenarios 群聊段**（cut:core，插话轮也可达——插话轮 system_prompt=原生协议+scene_prompt，无 manager 块）；strategy_guide 靶位教秘书精准选枚举（既有产物，惰性→激活）。
- W-AH 弃用分支：群聊退化关系选区+@场景营业默认，strategy_guide 保持惰性。
- 判据表述改为可证伪：「金丝雀群插话轮与 @轮的回复风格分别符合『枚举对应区/营业默认』的抽检表」。

**D4 · 台词库扩写政策**（任务包点名拍板项；建议：不阻塞 W3，冒烟后再拍）
- 19 唯一句（营业 9/温柔 4 唯一/腹黑 4 唯一+2 共享），close/intimate 场景密度偏低。
